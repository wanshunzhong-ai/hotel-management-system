# 酒店管理系统（Hotel Management System）

基于 **Spring Boot 3.3 + Thymeleaf + Spring Security + Spring Data JPA + MySQL 9** 的一体化酒店管理平台，
覆盖「房态总览 → 在线预订 → 入住登记 → 退房结算」的房间全生命周期。

## 功能总览

| 模块 | 说明 |
| --- | --- |
| 数据看板 | 入住率、今日预抵/预离、今日收款、近 7 日营收趋势（Chart.js）、房型销量分布、今日预抵/预离名单 |
| 房态一览 | 按楼层平铺的房态图，空闲 / 已预订 / 已入住 / 待清洁 / 维修中五种状态，支持改状态与一键清洁 |
| 房型 / 客房 | 房型（价格、床型、可住人数）与客房（房号、楼层、朝向）的增删改查与状态管理 |
| 预订管理 | 新建/编辑/取消/删除预订，按日期区间自动计算晚数与房费，**同一房间同一时段冲突自动拦截** |
| 入住 / 退房 | 预订 → 入住 → 退房状态流转，联动房间状态；退房自动生成账单 |
| 账单结算 | 房费 + 消费明细，押金 / 应收 / 应退自动计算，支持微信 / 支付宝 / 现金 / 银行卡收款，结账后锁定 |
| 客户档案 | 证件、联系方式、会员等级（普通/银卡/金卡/钻石），订单历史关联 |
| 客房部 · 派工验收 | 派工单（走客房 / 住客房 / 深度清洁）派给服务员 → 服务员完成 → 主管验收，**验收通过房间自动转「空闲」**，不合格打回重做（须填原因） |
| 客房部 · 迷你吧挂账 | 在住期间挂账酒水 / 客用品到房间，退房结账时**自动并入账单「其他消费」**并逐条生成明细 |
| 客房部 · 维修工单 | 报修 → 开工 → 完工 / 取消；空闲或待清洁房间报修自动置「维修中」，完工转「待清洁」，在住房间报修不占用房态 |
| 客房部 · 失物招领 | 拾遗登记（地点 / 拾获人）→ 关键词检索 → 客人认领登记，全程留痕 |
| 客房部 · 洗衣与布草 | 客衣（按件计价）与布草（内部周转、恒不计费）两类洗衣单，`已收件 → 洗涤中 → 已送回` 状态流转；布草库存三态台账（在库 / 洗涤中 / 已报废）与**安全库存预警**，领用 / 回库 / 报废均校验余量；客衣费退房结账时自动并入账单 |
| 客房部 · 扫码消费 | 消费目录维护（上/下架）+ 每个房间一枚 32 位随机令牌，可打印房间二维码；住客**免登录**扫码即可自助下单挂账，来源标记「住客扫码」可审计 |
| 客房部 · 查房评分 | 四项（床品 / 卫浴 / 设施 / 环境）各 0–25 分打分，≥80 合格；不合格自动派发一张深度清洁整改工单并把房间置「待清洁」，评分与整改单号可追溯 |
| 房态大屏 | 全屏墙挂式房态看板：按楼层平铺 + 实时入住率/各状态计数，10 秒轮询刷新，可暂停自动刷新、可切换日期 |
| 前台 · 押金与收款流水 | 收取押金 / 预订金 / 退还押金三类独立动作并全程留痕；**账单押金由收款流水汇总得出**（而非手填），退超余额直接拒绝；流水台账支持按类型/支付方式筛选与 CSV 导出 |
| 前台 · 交接班对账 | 当班净收款 + 按支付方式净额自动汇总，一键交班固化快照（含现金点清标记），交班单可打印 |
| 前台 · 发票管理 | 仅**已结账**账单可开票；可开额度 = 应收 − 已开有效发票，超额被拒；作废为**软删除**并释放额度；发票可打印 |
| 前台 · 应收账款台账 | 未结账单登记挂账单位与账期，按账龄排序、超期高亮，结清后自动从台账消失，支持 CSV 导出 |
| 前台 · 房价方案 | 协议价（按折扣率）与会员价（按会员等级）两类方案；预订时自动套价并**快照方案名与门市价**，事后可对账 |
| 前台 · 团队入住 | 多间订单归入同一团名 → 按团队批量办理入住，**逐间办理**，单间失败不影响其它 |
| 前台 · 换房与延迟退房 | 换房为独立动作（须填原因）并联动房态（旧房转待清洁 / 新房转已入住）；延迟退房按半日 / 全日档位加收，计入退房账单房费侧 |
| 客房部 · 客房主管角色 | **新增第四个角色「客房主管」**：用 Spring Security 的 `RoleHierarchy`（`ROLE_HOUSEKEEPING_SUPERVISOR > ROLE_HOUSEKEEPING`）声明继承，主管**自动获得客房服务的全部页面与动作权限**，无需在每个 matcher 里重复授权；需要额外放开给主管的动作（派工 / 验收 / 检查单模板 / 排班 / 耗材建档 / 布草外送）才显式写角色名 |
| 客房部 · 自行派工 | 客房主管可**自行派工**（巡检发现要深度清洁，不必再等前台建单），并进入**派工单详情页**（进程节点 + 清洁检查单执行区）；服务员仍不可派工（403） |
| 客房部 · 清洁标准检查单 | 按任务类型（走客房 / 住客房 / 深度清洁）自动带出对应检查项模板；派工时把模板**快照**成该单的执行清单，此后改模板、删模板都不影响历史单；**未逐项打勾不能提交完成**，一键全勾后可提交，主管验收通过 / 打回（打回须填原因） |
| 客房部 · 排班与工作量 | 早 / 中 / 晚三班次排班，**同一人同一天不可重复排班**；按人统计派工量、完成量、平均耗时，形成工作量视图 |
| 客房部 · 耗材出入库 | 耗材台账（品名 / 规格 / 单位 / 安全库存 / 当前库存）+ **出入库流水**（入库 / 领用 / 报废 / 盘点调整）；建档自动写一笔「初始入库」流水；**超库存领用被拒并提示差额**；**有流水的耗材不允许删除**；服务员可领用但不可建档 |
| 客房部 · 移动端现场上报 | `/hk` 员工入口（**须登录**，与免登录的住客 `/scan` 是两条独立路径）：扫房间上的**员工码**直达「房间操作台」，现场报修 / 登记失物 / 迷你吧挂账 / 改房态 / 一键完成工单；挂账沿用「该房间必须有在住订单」闸门 |
| 客房部 · 站内待办中心 | `/todos` **实时派生**待办（未完成工单 / 超时未完成 / 耗材与布草低于安全库存），不建消息表、不依赖推送设施；侧栏渲染待办数量角标；客房主管看全量，服务员只看「我的待办工单」 |
| 客房部 · 布草洗涤外包 | 布草外送批次（供应商 / 单价）`已送出 → 已收回 → 已结算` 流转，可取消；送出即在库→洗涤中、回收即洗涤中→在库（**数量守恒**）；**未回收不能结算**；超量外送被拒；交接单可打印 |
| 账号权限 | 管理员 / 前台接待 / 客房服务 / **客房主管**四种角色，基于 Spring Security 的 URL + 方法级权限隔离；客房服务只能进客房相关页面且不能建房/派工/验收，数据看板对其隐藏全部金额；派工与验收为「管理员 + 前台 + 客房主管」（权限对称，闭环不依赖单一岗位在岗）；第六批新增的收款流水 / 交接班 / 发票 / 应收 / 房价方案 / 团队 六类页面只对管理员与前台开放，**客房主管同样进不去** |

## 技术栈

- **后端**：Spring Boot 3.3.5（Web / Validation / AOP）、Spring Security 6、Spring Data JPA（Hibernate）
- **前端**：Thymeleaf 服务端渲染 + Bootstrap 5.3 + Bootstrap Icons + Chart.js（全部本地化，离线可用）
- **二维码**：ZXing `core`（只引 core，PNG 由 JDK 自带 `ImageIO` 输出，不拖入 jai-imageio / jcommander）
- **数据库**：MySQL 9（utf8mb4），启动时自动建表并初始化演示数据
- **构建**：Maven，JDK 17+（开发环境使用 JDK 21）

## 核心业务规则

- 订单状态机：`已预订 → 已入住 → 已退房`（可取消 / 删除，历史订单禁止删除）
- 冲突检测：创建/修改预订时校验同房间在 `[入住, 离店)` 区间内是否已有有效订单，同一房间加悲观锁，并发下单只能成功一单
- 房态语义：`room.status` 只表达**物理状态**（空闲 / 已入住 / 待清洁 / 维修中）；「某晚能不能卖」由预约表按日期实时推导，房态图支持选日期查看
- 账单：`应收合计 = 房费 + 其他消费 − 折扣`，`应退 = 押金 + 本次收款 − 应收合计`，收款必须足额才能结账；提前离店按实际住夜重算房费，差额记为「提前离店减免」
- 留痕：折扣 / 反结账 / 撤销挂账必须填原因并写入账单备注与操作日志，关键动作（入住 / 退房 / 结账 / 房态变更 / 派工 / 验收 / 报修 / 挂账·撤销挂账 / 失物 / 洗衣收件·洗涤·送回·取消 / 布草入库·领用·回库·报废 / 消费目录新增·修改 / 重置房间二维码 / 查房评分）全量审计，仅管理员可查
- 客房部闭环：派工 → 完成 → 验收通过自动「待清洁 → 空闲」；迷你吧挂账与**客衣洗涤费**退房时自动入账；维修报修 / 完工自动联动房态；查房不合格自动派发一张深度清洁整改工单并把房间转「待清洁」
- 洗衣计费口径：**布草恒不计费**（内部周转，金额强制归零、不关联订单）；客衣按 `单价 × 件数` 计费，`已收件 / 洗涤中 / 已送回` 三种状态都要收钱，**只有「已取消」不并入账单**（衣服都洗好送回了，钱当然得收）
- 布草台账：`在库 / 洗涤中 / 已报废` 三态互转，领用 / 回库 / 报废均先校验余量，超量直接拒绝并提示差多少件；低于安全库存的行高亮预警
- 扫码挂账安全：房间令牌由 `SecureRandom` 生成 32 位 Base62 串（约 190 bit 熵，不可枚举）；扫码页免登录，但**真正的闸门是「该房间当前必须有在住订单」**——空房即使拿到合法令牌也下不了单。令牌可一键重置让旧二维码立即失效，下单来源标记「住客扫码」，与前台手工录入可区分
- 查房评分：床品 / 卫浴 / 设施 / 环境四项各 0–25 分，合计 `≥80` 判合格；不合格自动生成整改派工单并把单号回写到评分记录上
- 押金口径（第六批）：账单上的押金**不再手工填写**，而是由 `payment_record` 收款流水汇总：`押金 = Σ(预订金 + 押金) − Σ(已退押金)`；退款超过当前余额直接拒绝，订单详情同时展示「预收款净额」与「可退余额」。预订金只在「已预订」状态可收，已入住 / 已离店一律拒绝
- 交班快照：交班时把当班「净收款」与**按支付方式净额**固化成一条 `shift_handover`，交班后不随后续流水变动；现金点清是独立标记，交班单可打印
- 发票额度：可开额度 = 账单应收 − 已开**未作废**发票合计；仅**已结账**账单可开票，超额被拒；作废是**软删除**（记录保留、状态置作废），作废后额度立即恢复
- 房价方案计价优先级：**固定价 > 折扣率 > 房型门市价**；下单时把方案名与当时的门市价一并快照到订单上，之后改方案或调房型价都不会篡改历史订单
- 换房联动：换房后**旧房转「待清洁」、新房转「已入住」**，原因写入订单备注与操作日志；新旧房间相同时直接拒绝
- 延迟退房加收：半日 / 全日两档，加收金额计入**退房账单的房费侧**（不是「其他消费」），已退房订单不可再改
- 团队入住：按团名把多间订单归并，批量入住**逐间办理**——单间失败（如已被占用）只跳过该间并回报，不影响其余房间
- 权限边界（第五批修补）：① 客房部**不能新建 / 修改客房**——`/rooms/save` 此前只在页面上藏了按钮、接口没拦，现已同时用 URL matcher 与动作级注解收口；② **派工与验收为「管理员 + 前台」**（第七批起再加入**客房主管**），客房服务员既不能派工也不能验收（不能自己验自己做的房），避免管理员不在岗时客房完成的房间卡在「待清洁」卖不出去；③ **撤销挂账须填原因**（写入操作日志留痕），且**客房部只能撤本人录入的挂账**，管理员 / 前台可撤任意一笔；④ 客房部看板的营收卡片、营收趋势图与名单金额**全部隐藏，且营收数据压根不下发**（不是只遮界面）
- 角色边界收口原则：界面隐藏只是体验层，真正的闸门必须在服务端——凡「页面藏了按钮」的动作，都必须同时在 URL 层或方法层有对应拦截
- 角色继承（第七批）：客房主管**不逐条复制**客房服务的授权，而是用 `RoleHierarchyImpl.fromHierarchy("ROLE_HOUSEKEEPING_SUPERVISOR > ROLE_HOUSEKEEPING")` 声明继承。URL 层的授权管理器会自动拾取 `RoleHierarchy` bean，但**方法级 `@PreAuthorize` 不会**——它走的是 `MethodSecurityExpressionHandler`，必须**显式 new 一个并 `setRoleHierarchy(...)`**，否则页面上能进、接口却 403（这一条在实现时踩到过，两处都得配）
- 检查单快照语义（第七批）：派工时把当时的检查项模板**复制**成该工单的 `task_checklist` 行，而不是运行时去 join 模板表。因此**删掉或停用模板不影响任何历史工单**——检查单是当时的作业标准，事后改标准不该改写历史记录
- 耗材库存口径（第七批）：`supply_item.stock` 是**派生的汇总值**，真相在 `supply_movement` 流水里（建档写一笔初始入库，领用 / 报废 / 盘点调整各写一笔）。领用前先校验余量、超量直接拒绝；**只要有过流水就不允许删台账**，否则库存对不上账
- 布草外送数量守恒（第七批）：送出 `在库 −= n, 洗涤中 += n`，回收 `洗涤中 −= n, 在库 += n`。**批次必须「已收回」才能结算**——没收回来的布草还没验货，结算就是把钱付给一个未知数；取消一个仍在「已送出」的批次会先把数量退回在库，避免布草永久挂在「洗涤中」凭空消失
- 站内待办不建表（第七批）：`/todos` 的条目是**查询时实时派生**的（未完成工单、超时未完成、低于安全库存的耗材与布草），没有消息表、没有定时任务、没有推送通道。理由是这些待办的判据全都在业务数据里，存一份副本只会引入「数据变了通知没变」的不一致；侧栏角标用 `@ControllerAdvice` 的 `@ModelAttribute` 全局注入一个 `todoCount`，避免每个 Controller 各写一遍
- 移动端两条路径（第七批）：`/scan/**`（住客，免登录，只有房间令牌 + 必须有在住订单）与 `/hk/**`（员工，**必须登录**）是**两条独立链路**，不共用鉴权。员工码与住客码并存于房间二维码页，扫员工码会要求先登录再跳房间操作台
