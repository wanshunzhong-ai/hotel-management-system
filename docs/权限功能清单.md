# 系统权限与功能清单（按身份）

> 依据当前代码逐条核对得出：`config/SecurityConfig.java`（URL 层）、各 `controller/*.java` 的 `@PreAuthorize`（动作层）、`templates/**` 的 `sec:authorize`（界面层）。
> 三层如果有不一致，会在「权限缺口」一节单独列出。

---

## 一、角色与登录入口

| 身份 | 角色码 | 演示账号 | 一句话职责（代码里的定义） |
| --- | --- | --- | --- |
| 管理员 | `ADMIN` | `admin` / `123456` | 系统全部权限 |
| 前台接待 | `RECEPTION` | `reception` / `123456` | 预订、入住、退房、结账 |
| 客房服务 | `HOUSEKEEPING` | `housekeeping` / `123456` | 房态查看与清洁维护 |
| 客房主管 | `HOUSEKEEPING_SUPERVISOR` | `supervisor` / `123456` | 客房排班、派工与验收（第七批新增） |
| （隐形）住客 | 无账号 | 房间二维码 | 免登录扫码下单，仅本房间、仅挂账 |

登录后统一跳 `/dashboard`；无权限请求 → `/error/403`；同一账号最多 5 个并发会话。

**角色继承**：客房主管不逐条复制客房服务的授权，而是由 `SecurityConfig` 的
`RoleHierarchyImpl.fromHierarchy("ROLE_HOUSEKEEPING_SUPERVISOR > ROLE_HOUSEKEEPING")` 声明继承关系。
因此凡是写着 `HOUSEKEEPING` 的 matcher 与 `@PreAuthorize`，主管**自动具备**；
只有需要额外放开给主管的动作（派工 / 验收 / 检查单模板 / 排班 / 耗材建档 / 布草外送）才显式列角色名。

> ⚠️ 实现注意：URL 层的授权管理器会自动拾取 `RoleHierarchy` bean，但**方法级 `@PreAuthorize` 不会**——
> 它用的是 `MethodSecurityExpressionHandler`，必须显式声明一个并 `setRoleHierarchy(...)`，
> 否则会出现「页面能进、接口 403」的不一致。

## 三、管理员（ADMIN）

### 3.1 已有功能（26 个模块全量）

- **经营概览**：数据看板（在住 / 空闲 / 出租率 / 今日营收 / 本月营收 / 累计营收 / 今日预抵预离 / 未结账单 / 客户数）、营收趋势图、房型分布图、房态构成条、今日预抵预离名单
- **前台业务**：预订全流程（建单、改单含换房、取消、删除、入住、退房、CSV 导出、可用房查询）；账单全流程（明细、追加消费、删除消费项、折扣、结账、**反结账**、打印、CSV 导出）；客户档案（增删改查、弹窗快速建档、搜索下拉）
- **房态管理**：房态一览（按楼层平铺、可切换日期看某晚可售）、房态大屏（全屏、10 秒轮询、可暂停）
- **客房服务**：派工与验收（建单、完成、**验收通过 / 打回重做**）、迷你吧挂账（录入、撤销）、查房评分（四项打分、不合格自动派整改单）、洗衣与布草（收件、状态流转、取消、台账管理、领用回库报废）、扫码消费（目录管理、二维码、令牌重置）、维修工单、失物招领
- **客房档案**：客房列表（增删改、房态变更、标记清洁）、房型设置
- **系统**：账号权限（员工增删改、重置密码、角色分配）、操作日志（按动作 / 关键词 / 日期筛选 + 分页）、个人中心

### 3.2 缺失功能

| 缺失项 | 说明 | 影响 |

## 六、权限缺口与修复记录（代码级）

这几条是「界面藏了但接口没拦」或「流程配置不合理」的实体问题，不是功能规划问题。
**四条均已在第五批修补中修复**，每条下方记录实际改法与理由；回归断言见 `scripts/opt4-test.sh` 第 8 节「权限加固回归」。

### 缺口 1　`POST /rooms/save` 未受保护 —— 客房部可绕过界面新增 / 修改客房

- **现状**：`SecurityConfig` 只把 `/rooms/new`、`/rooms/*/edit`、`/rooms/*/delete` 收给 `ADMIN`/`RECEPTION`，而 `/rooms/save` 落在 `.requestMatchers("/rooms/**")` → **三类角色均可访问**。
- **验证**：`room/list.html` 与 `room/board.html` 的新增 / 编辑 / 删除按钮对客房部已隐藏，但表单提交地址 `/rooms/save` 没有对应拦截。
- **影响**：客房部账号直接 POST 即可新建客房、修改房号 / 房型 / 状态，**越权写入基础档案**。
- **✅ 已修复**：`SecurityConfig` 的受限 matcher 补入 `/rooms/save`，同时在 `RoomController#save` 上加 `@PreAuthorize("hasAnyRole('ADMIN','RECEPTION')")` 做双保险——matcher 是顺序匹配，权限声明贴在被保护的方法上，日后有人调整 matcher 顺序也不会重新漏掉。

### 缺口 2　首页看板对客房部完全开放营收数据

- **现状**：`dashboard.html` 全文只有两处 `sec:authorize`（入住 / 退房按钮）。今日营收、本月营收、累计营收、在住预计房费、营收趋势图对**客房部全部可见**。
- **影响**：客房岗位不需要经营数据，属于**数据过曝**。
- **✅ 已修复**：营收卡、未结账单卡、客户档案卡、营收趋势整行、预离名单金额全部加 `sec:authorize="hasAnyRole('ADMIN','RECEPTION')"`；营收趋势的**数据常量与图表初始化脚本**也一并包进受控块，客房部的页面源码里不再出现任何金额（不是只遮界面）。客房部看板保留在住 / 空闲 / 出租率 / 今日预抵预离 / 房态构成 / 今日待办。

### 缺口 3　验收权过度集中，形成运营瓶颈

- **现状**：`POST /housekeeping/tasks/{id}/inspect` 是 `hasRole('ADMIN')` —— 前台与客房部都不能验收。
- **影响**：管理员不在岗时，客房部完成的房间**无法验收 → 无法回到空闲 → 无法出售**，直接影响可售房量。
- **✅ 已修复**：验收放开给 `ADMIN` + `RECEPTION`。理由：前台本来就有派工权（`POST /housekeeping/tasks` 限 ADMIN/RECEPTION），**派工与验收权限对称，闭环才跑得通**；客房部仍然不能验收（不能自己验自己做的房），模板按钮同步放开。若日后要区分客房主管，再引入 `HOUSEKEEPING_SUPERVISOR` 即可。

### 缺口 4　客房部可撤销任意挂账，且无原因字段

- **现状**：`POST /housekeeping/minibar/{id}/delete`（撤销挂账）对所有三角色开放，且**没有原因参数**。
- **影响**：挂账金额直接关系账单，客房部可撤销任何一笔（含前台录入的），无强制留痕。
- **✅ 已修复**：撤销原因改为**必填**并写入操作日志（`撤销原因：xxx` 进日志详情）；权限上「**客房部只能撤本人录入的挂账**，管理员 / 前台可撤任意一笔」——比一刀切收权限更贴合实际，自己录错的能自己纠，别人记的动不了。列表页对客房部只显示自己那几笔的撤销入口。
