## 一、正确性与数据可信度（优先修）

### 1.1 🔴 房态用单一 `status` 表达"时间维度"的占用 → 房态图与可售房数失真

**这是当前最需要处理的结构性问题。**

`ReservationService.create()` 第 92–96 行：

```java
// 当日预订视为马上入住 → 房间转为已预订占位
if (room.getStatus() == RoomStatus.AVAILABLE) {
    room.setStatus(RoomStatus.RESERVED);
    roomRepository.save(room);
}
```

注释写的是"当日预订"，但**代码没有任何日期判断**——不管订单是明天还是三个月后，只要房间当时是 `AVAILABLE`，就立刻被置为 `RESERVED`。

**用当前演示数据可以复现：**

```sql
SELECT r.room_no, r.status, v.check_in_date FROM room r
JOIN reservation v ON v.room_id = r.id WHERE r.status = 'RESERVED';
-- 507  RESERVED  2026-10-13   ← 今天是 10-10，房间实际空着
-- 602  RESERVED  2026-10-17
```

今天是 10-10，507 和 602 房间**物理上是空的、今天完全可以卖**，但因为 3 天后/7 天后有订单，房态图把它们显示为"已预订"，看板 `availableRooms` 也不把它们算作可售。

**连带影响（同一个根因）：**

`cancel()` → `releaseRoom()` 第 249–261 行，只要房间当前是 `RESERVED` 就无条件改回 `AVAILABLE`：

```java
if (fresh.getStatus() == RoomStatus.RESERVED) {
    fresh.setStatus(RoomStatus.AVAILABLE);
}
```

由于冲突校验只拦"日期区间重叠"，**同一房间允许存在多个不重叠的未来订单**（例如 10/20 一单、10/25 一单）。此时取消 10/20 那单，房间会被置为"空闲"，而 10/25 的订单仍然有效 —— 房态显示与实际可售性再次不一致。

**建议（两步走）：**

- **短期（改动小，先止血）**：`create()` 只在 `checkInDate` 等于今天时才置 `RESERVED`；`releaseRoom()` 释放前先查该房是否还存在其它 `BOOKED` 订单，有则不释放。
- **长期（推荐）**：把 `room.status` 的语义收敛为**物理状态**（`AVAILABLE` / `OCCUPIED` / `CLEANING` / `MAINTENANCE`），"某天能不能卖"**完全由预约表按日期区间实时计算**（`findAvailableBetween` 已经是正确实现了）。房态图增加一个**日期选择器**（默认今天），选哪天看哪天的可售情况。

> 顺带说：`findAvailableBetween()`（`RoomRepository:52`）的日期区间逻辑本身是对的，问题只出在 `room.status` 这一个字段上。收敛语义后，房态图和"可订房查询"就能统一到同一套口径。

### 1.2 🔴 结账不校验欠款，欠款单会被标记为"已结账"

`BillService.settle()` 第 103–132 行没有任何"收款是否足额"的判断：

```java
bill.setRefundAmount(deposit.add(paid).subtract(bill.getTotalAmount()));
bill.setStatus(BillStatus.SETTLED);   // 无条件置为已结账
```

若应收 1000，前台只录了 600，则 `refundAmount = -400`（负数代表欠款），但**状态直接变成"已结账"**，账单从此不可修改（`assertUnpaid` 拦截），欠款 400 也再无入口补收。

**建议：**

- `settle()` 增加校验：`deposit + paid < totalAmount` 时，要么拒绝并提示"还差 ¥400"，要么落为 `PARTIAL`（挂账）状态并允许后续补收
- `Bill` 增加 `欠款` 语义（可复用 `getDifference()`，目前该方法定义了却没人用）
- 前端结账弹窗实时显示"还差/应退"金额，避免前台算错

### 1.3 🔴 营收口径错误：用 `paidAmount` 统计营收，押金抵扣部分漏计

`DashboardService` 第 72–83、100–105 行：

```java
BigDecimal totalRevenue = sum(settled);            // sum 取的是 b.getPaidAmount()
BigDecimal todayRevenue = sum(...);
```

但 `settle()` 里 `paidAmount` 是**客人结算时补付的金额**，押金是单独字段：

```java
bill.setRefundAmount(deposit.add(paid).subtract(bill.getTotalAmount()));
```

举例：应收 1000，入住时收了押金 200，退房时客人再付 800 → `deposit=200, paid=800`。此时营收统计只算 800，**少算 200**。

`Bill.paidAmount` 的注释写的是"实收金额（含押金抵扣）"，与 `settle()` 的实际语义不符，说明这块口径本身就没想清楚。

**建议明确两个口径并分开统计：**

| 指标 | 正确算法 |
| --- | --- |
| 营收（经营口径） | `sum(totalAmount)` —— 应收合计 |
| 现金流入 | `sum(paidAmount + deposit)` |
| 当日营收 | 按 `settledAt` 分组聚合 `totalAmount` |

### 1.4 🔴 冲突校验存在并发窗口（check-then-act）

`ReservationService.assertNoConflict()` 第 242–247 行是典型的"先查后写"：

```java
long conflicts = reservationRepository.countConflicts(...);   // 查
if (conflicts > 0) { throw ... }
// ... 若干行之后才 save                                    // 写
```

两个前台同时给同一房间下同区间的订单时，在默认隔离级别下**双方都读不到对方未提交的行**，校验都会通过，最终两单都落库 → 到店无房。

**建议（任选其一）：**

- **最简单**：`create()`/`update()` 开头对房间加悲观锁
  `@Lock(LockModeType.PESSIMISTIC_WRITE)` + `findWithLockById(id)`，把同一房间的下单串行化
- **最彻底**：新建 `room_occupancy(room_id, stay_date)` 占用表，对 `(room_id, stay_date)` 建唯一索引，按天占位，靠数据库约束兜底

同时给 `reservation` 表补索引（见 2.7），否则冲突校验随数据增长会变慢。

### 1.5 🔴 提前退房不重算房费

`Reservation.getRoomAmount()`（`Reservation:95`）按 **计划** 晚数计算：

```java
return unitPrice.multiply(BigDecimal.valueOf(getNightCount()));   // checkOutDate - checkInDate
```

而 `ReservationService.checkOut()`（第 182–197 行）只写 `checkOutTime`，**没有回写 `checkOutDate`**。

结果：客人订 10/1–10/10（9 晚），10/5 提前离店，账单仍然收 9 晚房费，前台只能靠"追加消费"填负数来变通（见 2.6）。

**建议：**

- 退房时按实际住夜数（`ChronoUnit.DAYS.between(checkInDate, 实际退房日)`，不足一天按一天）重算 `roomAmount`，并在账单上体现"提前离店减免"
- 或保留计划价但增加显式的"早退减免"按钮，由前台决定

### 1.6 🟠 看板把全表账单加载进内存

`DashboardService:72`：

```java
List<Bill> settled = billRepository.findAll().stream()
        .filter(b -> b.getStatus() == BillStatus.SETTLED && b.getSettledAt() != null)
        .toList();
```

后面所有营收统计（总额、今日、本月、近 7 日趋势）都是对这个内存 List 做 stream 过滤。账单上万行后，**每次打开首页都要把整张表拉进 JVM**。

**建议**改成 SQL 聚合，例如：

```java
@Query("""
        select coalesce(sum(b.totalAmount), 0) from Bill b
        where b.status = com.hotel.hms.entity.BillStatus.SETTLED
        """)
BigDecimal sumSettledRevenue();

@Query("""
        select b.settledAt, coalesce(sum(b.totalAmount), 0) from Bill b
        where b.status = com.hotel.hms.entity.BillStatus.SETTLED
          and b.settledAt >= :from
        group by b.settledAt
        """)
List<Object[]> dailyRevenueSince(@Param("from") LocalDateTime from);
```

近 7 日趋势一次查询即可拿到，不必遍历全表。

**另外两个口径问题一并说明：**

- `setOccupancyRate` 只算 `OCCUPIED / total`（第 61–62 行），行业口径的出租率是 **已售房 / 可售房**（含已预订，且应排除维修房）
- `todayExpectedRevenue` 用的是在住订单的**全周期**房费（第 90–93 行），不是"今日一天的营收"，命名与含义不符

## 二、业务逻辑与边界

### 2.1 🟠 `hotel.max-advance-days` 是死配置

`application.yml:52` 定义了该配置，但**全项目没有任何地方读取它**（已 grep 确认）。而 `ReservationService.validateDates()` 第 237 行把上限**硬编码**成 365：

```java
if (ChronoUnit.DAYS.between(checkIn, checkOut) > 365) {
```

顺便说明：这里 365 限制的其实是**住店天数**，而配置名的语义是"最多可提前多少天预订"，两者根本不是一回事。

**建议**：注入配置，并明确两个约束——
`max-advance-days`（今天起算最多提前多少天预订）+ `max-stay-nights`（单次最多住多少晚）。

### 2.2 🟠 服务端未校验入住日期不能早于今天

`validateDates()`（第 230–240 行）只检查了"离店晚于入住"和"不超 365 晚"，**没有校验 `checkIn >= today`**。前端日期控件可能加了 `min`，但服务端不校验就形同虚设——直接 POST 就能建出昨天的订单，破坏"今日预抵"等看板统计。

**建议**：服务端加 `checkInDate.isBefore(LocalDate.now())` → 抛业务异常（补录历史订单的需求可用单独的管理员入口）。

### 2.3 🟠 最后一个管理员可被"降级"或"停用"

`UserService.delete()` 有保护（第 89–91 行）：

```java
if (db.getRole() == Role.ADMIN && countEnabledAdmins() <= 1) {
    throw new BusinessException("系统必须保留至少一个管理员账号");
}
```

但 **`update()`（第 62–81 行）没有同样的保护**——管理员可以把自己或唯一管理员的 `role` 改成 `RECEPTION`，或者 `enabled=false`。一旦发生，**系统再无管理员，账号管理功能永久锁死**（而且当前会话还可能因为 `enabled=false` 被踢出）。

**建议**：把这段保护抽成 `assertAdminRemainsAfterChange(target, newRole, newEnabled)`，在 `update()` 中同样调用。

顺带：`countEnabledAdmins()`（第 118–122 行）用 `findAll().stream().count()`，应换成 `countByRoleAndEnabledTrue(Role.ADMIN)`。

### 2.4 🟡 客户删除无引用检查，错误提示笼统

`CustomerService.delete()`（第 66–69 行）直接 `delete`，客户若有历史订单，会落到外键约束异常，由 `GlobalExceptionHandler:35` 兜底成一句"数据存在关联或重复，操作被拒绝。"——用户不知道**被什么关联**。

**建议**：删除前显式检查 `reservationRepository.existsByCustomerId(id)`，提示"该客户有 3 笔订单，无法删除"；酒店场景更推荐**软删除**（`deleted` 标记）保留历史档案。

### 2.6 🟠 账单缺"折扣/减免"与"反结账"

- **无折扣字段**：`Bill` 只有 房费 / 其他消费 / 押金 / 应收 / 实收 / 应退，没有"折扣"。前台想给协议价或抹零，只能靠"追加消费"填**负数单价**（`BillService.addItem` 第 82 行不校验负数），这是没设计的变通，无法审计。
- **无反结账**：结账后 `assertUnpaid` 一刀切锁死，一旦结错（付错方式、金额录错）无法冲正，只能改数据库。

**建议**：加 `discountAmount` 字段（应收 = 房费 + 消费 − 折扣）；加"反结账"操作（仅 ADMIN，需二次确认并记录原因）。

### 2.7 🟠 关键查询字段缺索引

已从 `information_schema.STATISTICS` 核对，现有索引只有主键 + 唯一键 + 外键：

| 表 | 缺失索引 | 影响的查询 |
| --- | --- | --- |
| `reservation` | `(room_id, check_in_date, check_out_date)` | 冲突校验 `countConflicts` |
| `reservation` | `status` | `countByStatus` / `findInHouse` |
| `reservation` | `check_in_date` / `check_out_date` | 看板"今日预抵/预离" |
| `bill` | `status` / `settled_at` | 看板营收、未结账单数 |

演示数据量（40 房 / 10 单）看不出来，真实酒店半年就有几万条订单，这些查询会全表扫。

**建议**：`@Table(indexes = {...})` 声明，或引入迁移脚本统一管理。

### 2.8 🟡 全表加载做计数

`UserService.countEnabledAdmins()`（见 2.3）。同类问题还有 `DashboardService` 的房型循环（第 118–121 行，每个房型查一次 `countByRoomTypeId`）——房型不多时影响有限，可用一次 `group by` 替代。

## 三、使用习惯与交互（前台一天会用上百次的地方）

### 3.1 🔴 预订时新建客户会丢失已填表单 —— 最高频的断链

电话订房是酒店最典型的场景：客人报姓名电话，前台边听边录。当前流程：

1. 在 `/reservations/new` 填好日期、房间、人数
2. 发现客户不在档案里 → 点旁边的"新建客户"按钮（`reservation/form.html:38`）
3. **跳到 `/customers/new`**，之前填的日期/房间/人数**全部丢失**
4. 保存客户后 `redirect:/customers`（`CustomerController:82`）——**回到客户列表，不是回预订页**
5. 前台要从头再走一遍预订流程

**建议**：客户选择框旁提供**内联新建**（Bootstrap Modal + 局部提交，不离开页面），保存成功后自动选中新客户。这是本清单里**投入产出比最高**的一项。

同时建议：`/customers/new` 支持 `?returnTo=/reservations/new` 参数，保存后原路返回（作为弹窗方案的降级实现）。

### 3.2 🟠 客户下拉全量渲染，无搜索

`ReservationController` 把所有客户塞进 `select`（`reservation/form.html:33-37`）：

```html
<option th:each="c : ${customers}" ...>
```

客户几百个时下拉框已经难用，上千个时页面体积和渲染都会出问题。

**建议**：换成带搜索的远程下拉（Select2 / Tomcat 的 `input + datalist` 也行），输入姓名或手机号后按关键词查前 20 条；同时把手机号作为主要搜索入口（前台报的通常是手机号）。

### 3.3 🟠 全站无分页

已确认：项目中**不存在任何 `Pageable` / `Page<T>` 用法**，所有列表接口返回 `List<T>`，模板里也没有分页控件。

| 列表 | 当前行为 |
| --- | --- |
| 订单列表 | 全部订单，`order by id desc` |
| 账单列表 | 全部账单 |
| 客户列表 | 全部客户 |
| 房间列表 | 全部房间 |
| 用户列表 | 全部账号 |

订单和账单是增长最快的两张表。**建议**：至少给订单、账单、客户三个列表加分页（Spring Data `Pageable` + 模板分页片段），默认 20 条/页。

### 3.4 🟠 订单/账单筛选维度太少

订单只有"关键词（订单号/姓名/手机号/房号）+ 单状态"。酒店前台高频需要的筛选条件缺失：

- **按入住/离店日期区间**（"下周有哪些预抵"）
- **按房间或楼层**
- **按应收/未结账状态**（账单页）
- 排序切换（默认按 id 倒序，无法按入住日期排）

另外"关键词 + 状态"这种组合，`ReservationRepository.search` 用的是 `like '%kw%'`，**前置通配符用不上索引**。若保留模糊搜索，建议同时支持按手机号**精确前缀**匹配（`phone like 'kw%'`，可命中索引）。

### 3.5 🟡 房态图不能直接发起业务动作

`room/board.html` 目前只支持"改房态"（且无二次确认，见下）。前台在房态图上看到某房空着，想直接办入住或建单，必须**跳出到订单页**。

**建议**：点击房间卡片弹出快捷菜单——办理入住（选在住订单）/ 新建预订（带入房间号）/ 标记维修 / 完成清洁。

**关于二次确认**：我逐个核对了所有危险操作表单，现状如下——

| 操作 | 二次确认 |
| --- | --- |
| 删除客户/房间/房型/账号/订单 | ✅ 有 |
| 取消订单 | ✅ 有 |
| 退房 | ✅ 有 |
| **办理入住**（3 处入口） | ❌ 无 |
| **房态图改状态** | ❌ 无 |

入住属于超高频操作，不加确认是**合理取舍**（加了反而拖慢前台）。但**房态图上把房间改成"维修中"会直接影响可售性**，建议对这一类变更补确认。

### 3.6 🟡 身份证与手机号未脱敏

客户列表直接明文展示 `idNo`、`phone`（模板中无任何脱敏处理）。客房部账号看不到客户模块（已被权限拦住），但前台同事之间互相可见全部证件号。

**建议**：列表页脱敏显示（`3301**********1234`），详情页按需"点击查看完整"（可记一次操作日志）。

### 3.7 🟡 无打印与导出

酒店实际运营中极高频，当前完全缺失：

- **账单小票 / 结账单打印**（含酒店抬头、消费明细、收退款）—— `bill/detail.html` 已有完整数据，加一个 `@media print` 样式即可
- **订单/账单导出 Excel**（对账、月结）

### 3.8 🟡 移动端/平板适配

侧边栏有移动端折叠逻辑（`app.js`），但**表格类页面在窄屏下没有降级方案**（房态图、订单表、账单明细都是宽表格）。酒店前台和客房部实际大量用平板。

**建议**：房态图在窄屏改为单列卡片流；表格用横向滚动 + 关键列固定。

### 3.9 🟡 缺少效率型交互

- 日期输入是原生 `input[type=date]`，没有"今天/明天/后天"快捷按钮（选离店日期时至少要有"次日"）
- 表单无自动聚焦（打开预订页焦点不在第一个字段）
- 全站无快捷键（如 `/` 聚焦搜索框、`Esc` 关闭弹层）
- 长表单无"未保存离开"提醒

### 3.10 🟡 硬删除导致历史断链

房间、房型、客户、账号都是物理删除（`delete`）。虽然 `GlobalExceptionHandler` 会拦住"有外键引用"的删除，但从业务角度：**房型被删后历史订单的房型信息就断了**（当前 `Room.roomType` 是 `EAGER` 关联，房型删不掉，实际操作是加删除限制——但提示不清晰）。

**建议**：改用软删除（`enabled` / `deleted` 标记），列表默认过滤，历史订单仍可追溯。

## 八、权限加固（第五批修补）：把「界面藏了按钮」与「服务端拦得住」对齐

第五批做完后按角色逐条核对权限，发现 4 处**界面与接口不一致**的问题。共同根因只有一个：
**把「页面上不显示按钮」当成了权限控制**。逐条修复如下。

### 8.1 `POST /rooms/save` 未被拦截 —— 客房部可绕过界面建房 / 改房（P0）

- **问题**：`SecurityConfig` 的受限 matcher 只写了 `/rooms/new`、`/rooms/*/edit`、`/rooms/*/delete`（都是 GET 表单页），
  而表单的**提交地址** `/rooms/save` 落进了下面的 `.requestMatchers("/rooms/**")` → 三类角色全部放行。
  界面按钮确实对客房部隐藏了（`room/list.html`、`room/board.html` 的 `sec:authorize`），但客房部账号直接 POST 就能新建客房、改房号 / 房型 / 状态。
- **修复**：matcher 补入 `/rooms/save`，同时在 `RoomController#save` 上加 `@PreAuthorize("hasAnyRole('ADMIN','RECEPTION')")` 做**双保险**——
  matcher 是顺序匹配的，权限声明贴在被保护的方法上，日后有人调整 matcher 顺序也不会重新漏掉。
- **教训**：新增/编辑类功能，**GET 表单页和 POST 提交地址是两个端点**，只拦其中一个等于没拦。

### 8.2 首页看板对客房部完全开放营收数据（P1，数据过曝）

- **问题**：`dashboard.html` 全文只有两处 `sec:authorize`（入住 / 退房按钮）。今日营收、本月营收、累计营收、
  在住预计房费、近 7 日营收趋势、预离名单里的房费——客房部全都看得到。
- **修复**：营收卡、未结账单卡、客户档案卡、营收趋势整行、预离名单金额全部加 `sec:authorize`；
  更进一步，**营收趋势的数据常量与图表初始化脚本也包进受控块** —— 客房部的页面源码里不再出现任何金额
  （只遮界面的话，`view-source` 仍能看到内联的营收数组）。客房部看板保留在住 / 空闲 / 出租率 / 今日预抵预离 / 房态构成 / 今日待办。
- **教训**：服务端渲染的页面，**隐藏 DOM 不等于不下发数据**；敏感数据要在模板层就不渲染。

### 8.3 验收权过度集中，形成运营死结（P0）

- **问题**：`POST /housekeeping/tasks/{id}/inspect` 是 `hasRole('ADMIN')` —— 前台与客房部都不能验收。
  而前台**本来就有派工权**（`POST /housekeeping/tasks` 限 ADMIN/RECEPTION）。
  结果是：管理员不在岗时，客房部完成的房间**验收不了 → 回不到「空闲」→ 卖不出去**，直接压可售房量。
- **修复**：验收放开给 `ADMIN` + `RECEPTION`。**派工与验收权限对称，闭环才跑得通**；
  客房部仍然不能验收（不能自己验自己做的房），模板按钮同步放开。
  若日后要区分「客房主管」，再引入 `HOUSEKEEPING_SUPERVISOR` 即可，不必现在就把角色体系铺大。
- **教训**：权限设计要看**流程能否闭环**，而不是只看单点是否安全。一个「只有管理员能做」的动作，
  如果它卡在业务主链路上，那就是可用性缺陷。

### 8.4 撤销挂账无门槛（P2，财务口径）

- **问题**：`POST /housekeeping/minibar/{id}/delete` 对所有三角色开放，且**没有原因参数**。
  撤销挂账等于往客人账单里退钱，客房部可以撤销任何一笔（包括前台录入的），且无强制留痕。
- **修复**：两道口子 —— ① **原因必填**，写入操作日志详情（`撤销原因：xxx`）；
  ② **客房部只能撤本人录入的挂账**，管理员 / 前台可撤任意一笔。
  比一刀切把权限收给管理员更贴合实际：自己录错的能自己纠，别人记的动不了。
  列表页对客房部只渲染自己那几笔的撤销入口（`canUndoOthers` + `currentUser` 两个 model 属性控制）。
- **教训**：涉及**金额**的撤销动作，「谁能做」与「为什么做」要同时约束，只约束其一都不够。

### 8.5 回归覆盖

`scripts/opt4-test.sh` 新增第 8 节「权限加固回归」，**28 项断言**逐条锁住上述修复（79 → 107 项）：

| 断言组 | 覆盖 |
| --- | --- |
| `/rooms/save` | 客房部 403 + 同令牌改房态放行（排除 CSRF 干扰的对照）/ 前台 200 + 未写入任何客房 |
| 看板隔离 | 客房部保留房态与待办；不含今日营收 / 累计营收 / 在住预计房费 / 营收趋势图；**源码中无金额符号**；管理员仍可见 |
| 验收权 | 客房部 403（原有用例保留）；前台 200 + 状态转 APPROVED + 验收人记录为前台 |
| 撤销挂账 | 不填原因被拒 / 撤他人被拒 / 撤本人成功 / 前台撤他人成功 / 撤销记录与原因均入审计日志 |

> 其中「日志计数」类断言刻意用 `>=` 而非 `==`：`operation_log` 只增不删（`clean-test-data.sh` 不清理它），
> 用精确计数第二次运行必然假失败。

## 九、第六批补充落地：前台接待补全（押金闭环 / 交班对账 / 发票 / 换房 / 迟退加收 / 团队 / 房价方案 / 应收）

第七节之前，前台的日常动作有一批**必须靠纸笔兜底**的缺口（《权限功能清单》4.2 列了 9 条）。
第六批一次性补齐，落点如下（2026-10-11）：

### 9.1 押金闭环：从「账单上一个手填字段」改成「独立收款流水」

- **原状**：`bill.deposit` 是账单单上的一个数字，谁填的都行；收押金 / 退押金没有独立动作，
  更没有凭证。前台实际做法是纸记一笔，结账时再对着纸敲进去。
- **改法**：新建 `payment_record` 收款流水表，记账 4 类流水 —— `DEPOSIT_IN`（押金）、
  `BOOKING_DEPOSIT`（预订金）、`DEPOSIT_REFUND`（退押金，负数）、结账收款。
  账单上的押金**不再手工填**，而是由流水汇总：

  ```
  押金 = Σ(预订金 + 押金) − Σ(已退押金)
  ```

  订单详情页同时显示「预收款净额」与「可退余额」，退押金超过余额**直接拒绝**。
- **业务门槛**：预订金只在「已预订」状态可收；已入住 / 已离店一律拒绝
  （预订金是占位的钱，房子都住了就不该再走预订金口径）。
- **为什么不做成账单字段**：流水是**可追溯的原始凭证**（谁、何时、什么方式、多少），
  而汇总值是可以随时重算的派生量。把派生量当存储字段，一旦有人手改就对不上账了。

### 9.2 交接班对账：把「当班净收款」固化成快照

- 交接班页按「当班」聚合收款流水，给出**净收款**（收款 − 退款）与**按支付方式净额**两个口径，
  带现金点清标记；一键交班写一条 `shift_handover` 快照。
- **快照而不是实时视图**：交班是要**签字确认**的动作，交班后陆续还会有新流水进来，
  如果交班单是实时算的，回头对账时数字会变，等于没有交班。所以交班必须固化。
- 交班单可打印（`/shift/{id}/print`），打印样式走 `@media print`。

### 9.3 发票：额度 = 应收 − 已开有效发票

- 只有**已结账**的账单能开票；可开额度动态计算，超额被拒。
- 作废是**软删除**（记录保留、状态置作废），作废后额度立即恢复 —— 发票是税务凭证，
  物理删除既不合规也丢了痕迹。
- 发票可打印（`/invoices/{id}/print`）。

### 9.4 换房留痕 + 房态联动

- 换房升为**独立动作**（不再是「改单」的副作用），原因必填，写入订单备注与操作日志；
  新旧房间相同时直接拒绝。
- 房态联动：**旧房转「待清洁」、新房转「已入住」**。
- 仍在同一把悲观锁下按 id 升序取锁，避免与并发下单互相死锁（沿用第三批 1.4 的做法）。

### 9.5 延迟退房加收

- 半日 / 全日两档，加收金额计入**退房账单的房费侧**（不是「其他消费」）——
  它本质是房费的时间延伸，放进「其他消费」会让房费口径失真、也影响 ADR 类指标。
- 已退房订单不可再改。

### 9.6 团队 / 批量入住

- 多间订单归入同一团名（`reservation.group_name`，订单详情页顶部显示团名徽章），
  团队工作台按团列成员，**批量办理入住逐间进行**：单间失败（如已被占用）只跳过该间并回报，
  不让一整团因为一间房失败而全部回滚。

### 9.7 房价方案：协议价 / 会员价

- 两类方案：`CORP`（协议价，按折扣率）与 `MEMBER`（会员价，按会员等级：银 95 折 / 金 9 折 / 钻石 85 折），
  另有固定价类型。计价优先级 **固定价 > 折扣率 > 房型门市价**。
- 下单时把**方案名与当时的门市价一起快照**到订单上 —— 之后改方案、调房型价，
  历史订单的计价依据都不会被篡改。
- 预订表单的价格联动是纯前端实时预览，服务端**重新算一遍**并以服务端结果为准
  （前端只负责让前台看得见）。

### 9.8 应收账款台账

- 未结账单可登记挂账单位与账期，台账按**账龄**排序、超期行高亮（`background:#fff5f5`），
  支持「仅看已挂账 / 仅看超期」筛选与 CSV 导出；结清后自动从台账消失。

### 9.9 权限

六个新模块（`/payments`、`/shift`、`/invoices`、`/receivables`、`/rate-plans`、`/groups`）在
**URL 层与动作层双层收口**为 `ADMIN` + `RECEPTION`（沿用 8.5 确立的原则），客房部一律 403。
验收测试第 11 节逐页断言了这一点。

### 9.10 本轮修掉的真实缺陷（都是验收测试抓出来的）

1. **`opt6-test.sh` 的前置清理长期静默失效（最隐蔽的一个）**
   前置清理写成了一条多语句批次，其中 `CREATE TEMPORARY TABLE tmp6_res` 后被**同一条 SQL 内引用两次**
   （`payment_record` 的 `reservation_id IN (...) OR bill_id IN (...)`），
   MySQL 抛 `ERROR 1137 Can't reopen table`。
   **多语句批次里任意一条报错会中断后续全部语句**，于是后面的 `DELETE FROM shift_handover`
   压根没执行 —— 残留记录让「交接班记录落库」断言每次重跑都失败，且表面看像是业务 bug。
   修法：**拆成一条语句一次调用**，并去掉临时表改用普通子查询；同时在注释里写明这两个坑。

2. **「换房」遗留的旧房会永久污染房态基线**
   换房后订单已改指新房，那间旧房**不再被任何订单引用**，
   `clean-test-data.sh` 按「测试订单占用过的房间」反查永远看不到它，
   于是永久残留一个「待清洁」。修法两层：
   ① `opt6-test.sh` 断言完房态联动后**立刻**把旧房复位（脚本自己知道旧房 id，最精确）；
   ② `clean-test-data.sh` 增加按**演示基线白名单**的兜底（基线非空闲房只有 606 维修中 / 607 待清洁），
      其余没有有效订单的非空闲房一律复位为空闲。

3. **房态复位必须早于订单删除**
   同样是 `clean-test-data.sh`：一旦订单先被删掉，就再也无法反查「哪些房是本轮测试动过的」。
   把复位语句提到删除之前，才能拿到房间 id。

4. **`func-test.sh` 的断言口径太粗（被新功能放大）**
   原断言 `grep -c '已入住'` 期望整页恰好 1 行，靠的是「详情页只有一个地方出现已入住」这个巧合。
   第六批给详情页加了**换房选择器**，它按房态列出候选房间，在住房间自然带「已入住」字样，
   整页计数变成 6 → 断言假失败。修法不是去改页面文案迁就测试，而是把断言收窄到
   **订单状态徽章**本身（`badge-soft ms-2 danger">已入住`，`danger` 在状态枚举里唯一）。
   **教训：用「整页文本计数」当断言，等于把无关改动的风险引到自己身上。**

验收：`scripts/opt6-test.sh` **104 项**断言；**七套件合计 518 项断言全绿**（原 414）。
基线复核：房态 34/1/1/4（AVAILABLE / CLEANING / MAINTENANCE / OCCUPIED）、
`payment_record` / `invoice` / `shift_handover` 清零、`rate_plan` 种子 4 条。

## 十、第七批补充落地：客房服务补全（客房主管 / 自行派工 / 清洁检查单 / 排班工作量 / 耗材出入库 / 移动端上报 / 待办中心 / 布草外送）

第五节末尾之后，客房岗位还留着一批**必须靠人脑记、靠纸笔兜底**的缺口
（《权限功能清单》5.2 当时列了 10 条，其中 8 条仍未落地）。第七批一次性补齐（2026-10-11）：

### 10.1 客房主管：用 `RoleHierarchy` 继承，而不是复制授权

- **原状**：系统只有「客房服务」一个客房角色。主管与服务员权限完全相同，
  既无法按级分工，也导致「管理动作」（派工 / 验收 / 排班）只能发给管理员或前台。
- **改法**：新增 `HOUSEKEEPING_SUPERVISOR`，并声明继承：

  ```java
  RoleHierarchyImpl.fromHierarchy("ROLE_HOUSEKEEPING_SUPERVISOR > ROLE_HOUSEKEEPING")
  ```

  凡是写着 `HOUSEKEEPING` 的 matcher 与 `@PreAuthorize`，主管**自动具备**；
  只有需要额外放开给主管的动作才显式写角色名（共 15 处 `@PreAuthorize`）。
- **为什么用继承而不是逐个补角色**：`SecurityConfig` 里客房相关的 matcher 有十来条，
  `@PreAuthorize` 也有几十处。逐个补既啰嗦又容易漏——**日后新增一个客房页面，
  忘了给主管授权就会静默失效**。继承把「主管是服务员的超集」这个事实**声明一次**，
  新增页面自动继承，不需要任何额外动作。这条和 8.5「权限双层收口」是同一个思路：
  把结构性约束交给框架，而不是指望人记得住。
- **⚠️ 实现踩到的坑**：URL 层的授权管理器会**自动拾取** `RoleHierarchy` bean，
  但方法级 `@PreAuthorize` **不会**——它走的是 `MethodSecurityExpressionHandler`。
  必须再显式声明一个 handler 并 `setRoleHierarchy(...)`：

  ```java
  @Bean
  static MethodSecurityExpressionHandler methodSecurityExpressionHandler(RoleHierarchy hierarchy) {
      DefaultMethodSecurityExpressionHandler h = new DefaultMethodSecurityExpressionHandler();
      h.setRoleHierarchy(hierarchy);
      return h;
  }
  ```

  不配这一句的症状是「**页面点得进去、提交按钮却 403**」——页面走 URL 层（继承生效），
  表单走方法层（继承没生效），两边不一致，排查时很容易误判成业务 bug。

### 10.2 清洁检查单：模板必须**快照**，不能运行时 join

- **原状**：查房是「四项各 25 分」的评分，不是逐项打勾的 checklist —— 标准不可复现，新人难上手。
- **改法**：建立检查项模板（按 `category` 分组：卫生 / 布草 / 设施 / 其他），
  派工时按任务类型（走客房 / 住客房 / 深度清洁）**把当时的模板复制成该工单的
  `task_checklist` 行**，而不是运行时去 join 模板表。
- **为什么必须快照**：检查单是**当时的作业标准**。如果明细是实时 join 出来的，
  那么今天改一次模板，上周所有已验收工单的「当时该做什么」全被改写——
  验收记录、打回记录、责任判定都会失去依据。快照之后，
  删模板、停用模板、改条目名，历史工单一律原样保留（有专门断言守住这条）。
- 执行侧：**未逐项打勾不能提交完成**；支持一键全勾（省去十几下手点）；
  执行人与打勾时间逐项留痕，主管验收时看得到是谁、什么时候勾的。

### 10.3 耗材出入库：`stock` 是派生值，流水才是真相

- **原状**：只有布草台账；客房六小件、清洁剂等易耗品完全没有账，物料成本无法追踪。
- **改法**：独立耗材台账 `supply_item`（品名 / 规格 / 单位 / 安全库存 / 当前库存）
  \+ 出入库流水 `supply_movement`（`IN` 入库 / `OUT` 领用 / `SCRAP` 报废 / `ADJUST` 盘点调整）。
  每笔流水都记 `stock_after` 快照，便于对账时定位是哪一笔把数字带偏的。
- **设计取舍**：`supply_item.stock` 保留为**冗余汇总值**（列表页要排序、要跟安全库存比，
  每次都现算成本高），但**建档时自动写一笔「初始入库」流水**，
  保证「流水累加 = stock」这个不变式从一开始就成立；
  **只要有过流水就不允许删台账**（否则账上少一份物料却查不到原因），
  想停用请走「停用」而不是删除。
- 业务门槛：超库存领用**直接拒绝并提示差多少件**（比只报「库存不足」有用）；
  服务员可领用 / 报废 / 盘点，但**建档只有管理员、前台与客房主管可以做**。

### 10.4 布草外送的数量守恒

- **原状**：布草能进出库，但**外送洗涤这一环没账**——送出去多少、回来多少、
  结算多少全靠口头，外包环节是黑洞。
- **改法**：外送批次 `outsource_batch` + 明细 `outsource_item`，
  状态 `已送出 → 已收回 → 已结算`（可取消）。数量严格守恒：

  ```
  送出：在库 −= n，洗涤中 += n
  回收：洗涤中 −= n，在库 += n
  ```

- **两道业务闸门**：① **未回收不能结算**——没收回来的布草还没验货，
  结算等于把钱付给一个未知数；② 超量外送被拒（在库只有 90 件却要送 100 件，
  直接拒绝而不是把在库做成负数）。
- 取消一个仍在「已送出」状态的批次会**先把数量退回在库**再删批次——
  否则那些件数会永久挂在「洗涤中」凭空消失（这一条在 `clean-test-data.sh` 里也做了同样处理）。
- 交接单可打印（`@media print`），交给洗涤公司签字。

### 10.5 站内待办中心：不建消息表

- **原状**：工单积压、耗材告急都要靠人主动刷新页面才会发现，容易漏事。
- **改法**：`/todos` 把待办**在查询时实时派生**：未完成工单、超时未完成、
  低于安全库存的耗材与布草。**没有消息表、没有定时任务、没有推送通道。**
- **为什么不建表**：这些待办的判据**本来就在业务数据里**，存一份副本只会引入
  「数据变了、通知没变」的不一致，还要额外处理已读 / 未读 / 过期清理。
  派生方案的代价只是「每次打开页面算一遍」——而它天然永远是对的。
- 侧栏角标用 `@ControllerAdvice` 的 `@ModelAttribute` **全局注入一个 `todoCount`**，
  避免每个 Controller 各写一遍（`layout.html` 是共用片段，只有全局属性才到得了）。
- **按角色裁剪**：客房主管看到全量调度类条目，服务员只看到「我的待办工单」，
  不显示调度视角的条目（有断言守住）。
- 局限：这不等于「通知中心」——没有消息历史、没有主动推送（邮件 / 短信 / 站内信仍缺），
  只是把「要人去查」变成「打开就有」，`权限功能清单` 第七节如实标注为 ◐。

### 10.6 移动端两条链路必须分开

- **原状**：客房服务员在房间里发现马桶漏水或客人遗留充电器，得回电脑前台操作，现场作业效率低。
- **改法**：新增 `/hk/**` **员工入口（必须登录）**，扫房间上的**员工码**直达「房间操作台」，
  可现场报修 / 登记失物 / 迷你吧挂账 / 改房态 / 一键完成工单。
- **为什么不能复用 `/scan/**`**：住客扫码链路是**免登录**的，唯一凭据是房间令牌，
  闸门是「该房间当前必须有在住订单」。员工链路要求的是**身份**（谁做的、算谁的工单），
  两条链路的信任模型完全不同——**共用一套鉴权迟早会把员工操作暴露成免登录接口**。
  所以住客码与员工码并存于房间二维码页，各走各的链路。
- 挂账沿用「必须有在住订单」闸门：空房即使有合法员工码也挂不上账（有断言守住）。

### 10.7 权限边界：角色继承是**单向**的

客房主管继承了客房服务的一切，但**进不了**前台的六个资金模块
（收款流水 / 交接班 / 发票 / 应收台账 / 房价方案 / 团队）与客户 / 订单 / 账单 / 账号 / 日志。
验收测试第 9 节**逐页断言** 403。这一条特意写清楚：
「继承」只沿 `SUPERVISOR > HOUSEKEEPING` 一条线走，**不会反向把前台的权限漏下来**。

### 10.8 本轮修掉的真实缺陷（六个，都在验收过程中现形）

1. **`RoleHierarchy` 只配了 URL 层，方法层漏配（最隐蔽）**
   症状：主管能打开派工页，点「派工」提交却 403。因为 URL 层的授权管理器自动拾取了
   `RoleHierarchy` bean，而方法级 `@PreAuthorize` 用的是另一条链路
   （`MethodSecurityExpressionHandler`），不显式 `setRoleHierarchy` 就不认继承。
   修法见 10.1。**教训：Spring Security 里「同一份授权规则」在不同层由不同组件解释，
   配一处不等于配全。**

2. **`${rotation[s]}` 传枚举当 Map 下标 → 页面 500**
   `housekeeping/schedule.html` 里用 `DayShift` 枚举去索引 `Map<DayShift, List<...>>`，
   Thymeleaf 报 `IllegalArgumentException: The target type java.lang.Enum does not refer to an enum`。
   修法：改用 `${rotation.get(s)}`（显式方法调用，绕开 SpEL 对枚举下标的处理）。
   定位手段是**关掉模板缓存 + 把模板前缀指到源码目录**，改一行刷一次，逐行二分。

3. **`consumables/list.html` 一处表达式写法把整页打挂（存量缺陷，非本批引入）**
   原文 `th:text="'共 ' + ${rooms.size()} 间'"` 把字符串字面量与 `${...}` 混写，
   Thymeleaf 抛 `Could not parse as expression`，最终以
   `HttpMessageNotWritableException: No converter for LinkedHashMap` 的形式冒出来（错误信息完全指错方向）。
   修法是改用字面量替换语法 `th:text="|共 ${rooms.size()} 间|"`。
   **这条经 `git show HEAD` 确认在本批开工前就存在**——是顺手修掉的存量缺陷，
   不是本批引入的，单独记一笔以免混淆。

4. **`opt7-test.sh` 自身的幂等性缺陷（验收测试自己抓出来的）**
   首次交付时把**基线断言写在了幂等清理之前**，而且清理没覆盖第七批移动端上报产生的
   三类现场数据（报修工单 / 失物登记 / 迷你吧挂账）。
   后果：**第一次跑全绿，第二次跑 4 项失败**（期望 1 条、实际 3 条——累加了上一轮的残留），
   看起来像业务 bug，实际是测试自身的顺序问题。
   修法：① 基线断言一律挪到清理**之后**；② 清理补上这三张表，
   并在删报修工单**之前**把被测试置成「维修中」的房间复位（且只认测试工单涉及的房间，
   不误伤演示基线里 606 的「维修中」）。修完**连跑两遍结果完全一致（均 0 失败）**。

5. **`func-test.sh` / `opt4-test.sh` / `opt6-test.sh` 里三条口径过粗的断言（被本批新增数据放大）**
   - `opt4` 断言「按状态筛选：已打回为空」硬编码期望 `0`，而它假设的是
     **整个库里不存在任何 REJECTED 工单**。第七批的打回流程测试留下一条 REJECTED，
     这条断言立刻假失败。修法不是去删数据迁就断言，而是改成
     **与库中同口径计数比对**（页面条数 == `select count(*) ... REJECTED`），
     断言从此与「库里有没有别的测试残留」解耦。
   - `opt6` 断言「作废后可开额度恢复」，拿**页面上的格式化金额**（`可开 ￥1,332.00`，带千分位）
     去硬比**库里的原始金额**（`1332.00`，不带千分位）。它此前能过，纯属运气：
     该单的房间由 `pick_idle_room` 动态选，**房价过千就带逗号、不过千就不带**——
     也就是说这条断言的成败取决于「今天恰好选到哪间房」。修法是先 `tr -d ','` 去掉分隔符再比。
   - **教训同 9.10 第 4 条**：断言不要去假设「全局只有一个」、也不要假设「页面数字的格式」，
     要**拿页面数字跟数据库对**（并且先归一化格式）。
     **本轮把三条都改成与库对齐的口径后，八套件连续两轮复跑全绿。**

6. **`/laundry/outsourcing/{id}` 交接单详情页整页打挂（LAZY 集合 + OSIV 已关）——本批最隐蔽的一条**
   症状：交接单打印页实际是错误页，但 **HTTP 状态码是 200**，而且页面前半截已经把
   「布草外送交接单」渲染出来了，于是 `has "交接单可打印" ... "布草外送交接单"` 断言匹配成功——
   **坏页面被测试判成 PASS**，八套件「全绿」里一直藏着这一条。
   根因：`OutsourceBatch.items` 是 `@OneToMany(fetch = LAZY)`，而项目显式关掉了 OSIV
   （`spring.jpa.open-in-view: false`）。`OutsourceService.get()` 用 `findById` 返回的是**游离实体**，
   事务一结束懒集合就没初始化，模板里 `th:each="i : ${batch.items}"` 一迭代即
   `LazyInitializationException: ... OutsourceBatch.items: could not initialize proxy - no Session`。
   为什么状态码是 200：模板是**边渲染边写响应**的，异常抛出时响应体已按 200 提交，
   Spring 的全局错误页被**追写进同一个响应体**——于是响应 = 「半截正常页面 + 尾部错误页」。
   修法：照既有的 `BillRepository#findDetailById` 范式，给 `OutsourceBatchRepository` 加
   `@Query("select distinct b from OutsourceBatch b left join fetch b.items where b.id = :id")`，
   `get()` 改走它，在事务内一次把洗涤明细抓出来。
   **测试侧加固（比修 bug 本身更重要）**：`opt7-test.sh` 新增 `err_page()` / `pageok()`，
   凡「页面能正常打开」的断言一律走 `pageok`——**既看状态码、也看正文不是错误页、再看关键元素在没在**；
   交接单页在「已送出 / 已收回 / 已结算」三个状态下各断一次，并把明细品名（只在 `items` 循环里出现）
   作为必现关键字，懒加载再退化就会被立刻打出来。
   **教训：只看 HTTP 状态码的页面断言是不可信的**——响应一旦提交，错误页同样挂在 200 上。
   顺带做了同类风险普查：全库 `@OneToMany` 只有两处（`Bill.items` / `OutsourceBatch.items`），
   现均走 fetch join，此类缺陷清零。
