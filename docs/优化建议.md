## 一、正确性与数据可信度（优先修）

### 1.1 🔴 房态用单一 `status` 表达"时间维度"的占用 → 房态图与可售房数失真

**这是当前最需要处理的结构性问题。**

`ReservationService.create()` 第 92–96 行：

```java
// 当日预订视为马上入住 → 房间转为已预订占位
if (room.getStatus() == RoomStatus.AVAILABLE) {
    room.setStatus(RoomStatus.RESERVED);
    roomRepository.save(room);
}
```

注释写的是"当日预订"，但**代码没有任何日期判断**——不管订单是明天还是三个月后，只要房间当时是 `AVAILABLE`，就立刻被置为 `RESERVED`。

**用当前演示数据可以复现：**

```sql
SELECT r.room_no, r.status, v.check_in_date FROM room r
JOIN reservation v ON v.room_id = r.id WHERE r.status = 'RESERVED';
-- 507  RESERVED  2026-10-13   ← 今天是 10-10，房间实际空着
-- 602  RESERVED  2026-10-17
```

今天是 10-10，507 和 602 房间**物理上是空的、今天完全可以卖**，但因为 3 天后/7 天后有订单，房态图把它们显示为"已预订"，看板 `availableRooms` 也不把它们算作可售。

**连带影响（同一个根因）：**

`cancel()` → `releaseRoom()` 第 249–261 行，只要房间当前是 `RESERVED` 就无条件改回 `AVAILABLE`：

```java
if (fresh.getStatus() == RoomStatus.RESERVED) {
    fresh.setStatus(RoomStatus.AVAILABLE);
}
```

由于冲突校验只拦"日期区间重叠"，**同一房间允许存在多个不重叠的未来订单**（例如 10/20 一单、10/25 一单）。此时取消 10/20 那单，房间会被置为"空闲"，而 10/25 的订单仍然有效 —— 房态显示与实际可售性再次不一致。

**建议（两步走）：**

- **短期（改动小，先止血）**：`create()` 只在 `checkInDate` 等于今天时才置 `RESERVED`；`releaseRoom()` 释放前先查该房是否还存在其它 `BOOKED` 订单，有则不释放。
- **长期（推荐）**：把 `room.status` 的语义收敛为**物理状态**（`AVAILABLE` / `OCCUPIED` / `CLEANING` / `MAINTENANCE`），"某天能不能卖"**完全由预约表按日期区间实时计算**（`findAvailableBetween` 已经是正确实现了）。房态图增加一个**日期选择器**（默认今天），选哪天看哪天的可售情况。

> 顺带说：`findAvailableBetween()`（`RoomRepository:52`）的日期区间逻辑本身是对的，问题只出在 `room.status` 这一个字段上。收敛语义后，房态图和"可订房查询"就能统一到同一套口径。

### 1.2 🔴 结账不校验欠款，欠款单会被标记为"已结账"

`BillService.settle()` 第 103–132 行没有任何"收款是否足额"的判断：

```java
bill.setRefundAmount(deposit.add(paid).subtract(bill.getTotalAmount()));
bill.setStatus(BillStatus.SETTLED);   // 无条件置为已结账
```

若应收 1000，前台只录了 600，则 `refundAmount = -400`（负数代表欠款），但**状态直接变成"已结账"**，账单从此不可修改（`assertUnpaid` 拦截），欠款 400 也再无入口补收。

**建议：**

- `settle()` 增加校验：`deposit + paid < totalAmount` 时，要么拒绝并提示"还差 ¥400"，要么落为 `PARTIAL`（挂账）状态并允许后续补收
- `Bill` 增加 `欠款` 语义（可复用 `getDifference()`，目前该方法定义了却没人用）
- 前端结账弹窗实时显示"还差/应退"金额，避免前台算错

### 1.3 🔴 营收口径错误：用 `paidAmount` 统计营收，押金抵扣部分漏计

`DashboardService` 第 72–83、100–105 行：

```java
BigDecimal totalRevenue = sum(settled);            // sum 取的是 b.getPaidAmount()
BigDecimal todayRevenue = sum(...);
```

但 `settle()` 里 `paidAmount` 是**客人结算时补付的金额**，押金是单独字段：

```java
bill.setRefundAmount(deposit.add(paid).subtract(bill.getTotalAmount()));
```

举例：应收 1000，入住时收了押金 200，退房时客人再付 800 → `deposit=200, paid=800`。此时营收统计只算 800，**少算 200**。

`Bill.paidAmount` 的注释写的是"实收金额（含押金抵扣）"，与 `settle()` 的实际语义不符，说明这块口径本身就没想清楚。

**建议明确两个口径并分开统计：**

| 指标 | 正确算法 |
| --- | --- |
| 营收（经营口径） | `sum(totalAmount)` —— 应收合计 |
| 现金流入 | `sum(paidAmount + deposit)` |
| 当日营收 | 按 `settledAt` 分组聚合 `totalAmount` |

### 1.4 🔴 冲突校验存在并发窗口（check-then-act）

`ReservationService.assertNoConflict()` 第 242–247 行是典型的"先查后写"：

```java
long conflicts = reservationRepository.countConflicts(...);   // 查
if (conflicts > 0) { throw ... }
// ... 若干行之后才 save                                    // 写
```

两个前台同时给同一房间下同区间的订单时，在默认隔离级别下**双方都读不到对方未提交的行**，校验都会通过，最终两单都落库 → 到店无房。

**建议（任选其一）：**

- **最简单**：`create()`/`update()` 开头对房间加悲观锁
  `@Lock(LockModeType.PESSIMISTIC_WRITE)` + `findWithLockById(id)`，把同一房间的下单串行化
- **最彻底**：新建 `room_occupancy(room_id, stay_date)` 占用表，对 `(room_id, stay_date)` 建唯一索引，按天占位，靠数据库约束兜底

同时给 `reservation` 表补索引（见 2.7），否则冲突校验随数据增长会变慢。

### 1.5 🔴 提前退房不重算房费

`Reservation.getRoomAmount()`（`Reservation:95`）按 **计划** 晚数计算：

```java
return unitPrice.multiply(BigDecimal.valueOf(getNightCount()));   // checkOutDate - checkInDate
```

而 `ReservationService.checkOut()`（第 182–197 行）只写 `checkOutTime`，**没有回写 `checkOutDate`**。

结果：客人订 10/1–10/10（9 晚），10/5 提前离店，账单仍然收 9 晚房费，前台只能靠"追加消费"填负数来变通（见 2.6）。

**建议：**

- 退房时按实际住夜数（`ChronoUnit.DAYS.between(checkInDate, 实际退房日)`，不足一天按一天）重算 `roomAmount`，并在账单上体现"提前离店减免"
- 或保留计划价但增加显式的"早退减免"按钮，由前台决定

### 1.6 🟠 看板把全表账单加载进内存

`DashboardService:72`：

```java
List<Bill> settled = billRepository.findAll().stream()
        .filter(b -> b.getStatus() == BillStatus.SETTLED && b.getSettledAt() != null)
        .toList();
```

后面所有营收统计（总额、今日、本月、近 7 日趋势）都是对这个内存 List 做 stream 过滤。账单上万行后，**每次打开首页都要把整张表拉进 JVM**。

**建议**改成 SQL 聚合，例如：

```java
@Query("""
        select coalesce(sum(b.totalAmount), 0) from Bill b
        where b.status = com.hotel.hms.entity.BillStatus.SETTLED
        """)
BigDecimal sumSettledRevenue();

@Query("""
        select b.settledAt, coalesce(sum(b.totalAmount), 0) from Bill b
        where b.status = com.hotel.hms.entity.BillStatus.SETTLED
          and b.settledAt >= :from
        group by b.settledAt
        """)
List<Object[]> dailyRevenueSince(@Param("from") LocalDateTime from);
```

近 7 日趋势一次查询即可拿到，不必遍历全表。

**另外两个口径问题一并说明：**

- `setOccupancyRate` 只算 `OCCUPIED / total`（第 61–62 行），行业口径的出租率是 **已售房 / 可售房**（含已预订，且应排除维修房）
- `todayExpectedRevenue` 用的是在住订单的**全周期**房费（第 90–93 行），不是"今日一天的营收"，命名与含义不符

## 二、业务逻辑与边界

### 2.1 🟠 `hotel.max-advance-days` 是死配置

`application.yml:52` 定义了该配置，但**全项目没有任何地方读取它**（已 grep 确认）。而 `ReservationService.validateDates()` 第 237 行把上限**硬编码**成 365：

```java
if (ChronoUnit.DAYS.between(checkIn, checkOut) > 365) {
```

顺便说明：这里 365 限制的其实是**住店天数**，而配置名的语义是"最多可提前多少天预订"，两者根本不是一回事。

**建议**：注入配置，并明确两个约束——
`max-advance-days`（今天起算最多提前多少天预订）+ `max-stay-nights`（单次最多住多少晚）。

### 2.2 🟠 服务端未校验入住日期不能早于今天

`validateDates()`（第 230–240 行）只检查了"离店晚于入住"和"不超 365 晚"，**没有校验 `checkIn >= today`**。前端日期控件可能加了 `min`，但服务端不校验就形同虚设——直接 POST 就能建出昨天的订单，破坏"今日预抵"等看板统计。

**建议**：服务端加 `checkInDate.isBefore(LocalDate.now())` → 抛业务异常（补录历史订单的需求可用单独的管理员入口）。

### 2.3 🟠 最后一个管理员可被"降级"或"停用"

`UserService.delete()` 有保护（第 89–91 行）：

```java
if (db.getRole() == Role.ADMIN && countEnabledAdmins() <= 1) {
    throw new BusinessException("系统必须保留至少一个管理员账号");
}
```

但 **`update()`（第 62–81 行）没有同样的保护**——管理员可以把自己或唯一管理员的 `role` 改成 `RECEPTION`，或者 `enabled=false`。一旦发生，**系统再无管理员，账号管理功能永久锁死**（而且当前会话还可能因为 `enabled=false` 被踢出）。

**建议**：把这段保护抽成 `assertAdminRemainsAfterChange(target, newRole, newEnabled)`，在 `update()` 中同样调用。

顺带：`countEnabledAdmins()`（第 118–122 行）用 `findAll().stream().count()`，应换成 `countByRoleAndEnabledTrue(Role.ADMIN)`。

### 2.4 🟡 客户删除无引用检查，错误提示笼统

`CustomerService.delete()`（第 66–69 行）直接 `delete`，客户若有历史订单，会落到外键约束异常，由 `GlobalExceptionHandler:35` 兜底成一句"数据存在关联或重复，操作被拒绝。"——用户不知道**被什么关联**。

**建议**：删除前显式检查 `reservationRepository.existsByCustomerId(id)`，提示"该客户有 3 笔订单，无法删除"；酒店场景更推荐**软删除**（`deleted` 标记）保留历史档案。

### 2.6 🟠 账单缺"折扣/减免"与"反结账"

- **无折扣字段**：`Bill` 只有 房费 / 其他消费 / 押金 / 应收 / 实收 / 应退，没有"折扣"。前台想给协议价或抹零，只能靠"追加消费"填**负数单价**（`BillService.addItem` 第 82 行不校验负数），这是没设计的变通，无法审计。
- **无反结账**：结账后 `assertUnpaid` 一刀切锁死，一旦结错（付错方式、金额录错）无法冲正，只能改数据库。

**建议**：加 `discountAmount` 字段（应收 = 房费 + 消费 − 折扣）；加"反结账"操作（仅 ADMIN，需二次确认并记录原因）。

### 2.7 🟠 关键查询字段缺索引

已从 `information_schema.STATISTICS` 核对，现有索引只有主键 + 唯一键 + 外键：

| 表 | 缺失索引 | 影响的查询 |
| --- | --- | --- |
| `reservation` | `(room_id, check_in_date, check_out_date)` | 冲突校验 `countConflicts` |
| `reservation` | `status` | `countByStatus` / `findInHouse` |
| `reservation` | `check_in_date` / `check_out_date` | 看板"今日预抵/预离" |
| `bill` | `status` / `settled_at` | 看板营收、未结账单数 |

演示数据量（40 房 / 10 单）看不出来，真实酒店半年就有几万条订单，这些查询会全表扫。

**建议**：`@Table(indexes = {...})` 声明，或引入迁移脚本统一管理。

### 2.8 🟡 全表加载做计数

`UserService.countEnabledAdmins()`（见 2.3）。同类问题还有 `DashboardService` 的房型循环（第 118–121 行，每个房型查一次 `countByRoomTypeId`）——房型不多时影响有限，可用一次 `group by` 替代。

## 三、使用习惯与交互（前台一天会用上百次的地方）

### 3.1 🔴 预订时新建客户会丢失已填表单 —— 最高频的断链

电话订房是酒店最典型的场景：客人报姓名电话，前台边听边录。当前流程：

1. 在 `/reservations/new` 填好日期、房间、人数
2. 发现客户不在档案里 → 点旁边的"新建客户"按钮（`reservation/form.html:38`）
3. **跳到 `/customers/new`**，之前填的日期/房间/人数**全部丢失**
4. 保存客户后 `redirect:/customers`（`CustomerController:82`）——**回到客户列表，不是回预订页**
5. 前台要从头再走一遍预订流程

**建议**：客户选择框旁提供**内联新建**（Bootstrap Modal + 局部提交，不离开页面），保存成功后自动选中新客户。这是本清单里**投入产出比最高**的一项。

同时建议：`/customers/new` 支持 `?returnTo=/reservations/new` 参数，保存后原路返回（作为弹窗方案的降级实现）。

### 3.2 🟠 客户下拉全量渲染，无搜索

`ReservationController` 把所有客户塞进 `select`（`reservation/form.html:33-37`）：

```html
<option th:each="c : ${customers}" ...>
```

客户几百个时下拉框已经难用，上千个时页面体积和渲染都会出问题。

**建议**：换成带搜索的远程下拉（Select2 / Tomcat 的 `input + datalist` 也行），输入姓名或手机号后按关键词查前 20 条；同时把手机号作为主要搜索入口（前台报的通常是手机号）。

### 3.3 🟠 全站无分页

已确认：项目中**不存在任何 `Pageable` / `Page<T>` 用法**，所有列表接口返回 `List<T>`，模板里也没有分页控件。

| 列表 | 当前行为 |
| --- | --- |
| 订单列表 | 全部订单，`order by id desc` |
| 账单列表 | 全部账单 |
| 客户列表 | 全部客户 |
| 房间列表 | 全部房间 |
| 用户列表 | 全部账号 |

订单和账单是增长最快的两张表。**建议**：至少给订单、账单、客户三个列表加分页（Spring Data `Pageable` + 模板分页片段），默认 20 条/页。

### 3.4 🟠 订单/账单筛选维度太少

订单只有"关键词（订单号/姓名/手机号/房号）+ 单状态"。酒店前台高频需要的筛选条件缺失：

- **按入住/离店日期区间**（"下周有哪些预抵"）
- **按房间或楼层**
- **按应收/未结账状态**（账单页）
- 排序切换（默认按 id 倒序，无法按入住日期排）

另外"关键词 + 状态"这种组合，`ReservationRepository.search` 用的是 `like '%kw%'`，**前置通配符用不上索引**。若保留模糊搜索，建议同时支持按手机号**精确前缀**匹配（`phone like 'kw%'`，可命中索引）。

### 3.5 🟡 房态图不能直接发起业务动作

`room/board.html` 目前只支持"改房态"（且无二次确认，见下）。前台在房态图上看到某房空着，想直接办入住或建单，必须**跳出到订单页**。

**建议**：点击房间卡片弹出快捷菜单——办理入住（选在住订单）/ 新建预订（带入房间号）/ 标记维修 / 完成清洁。

**关于二次确认**：我逐个核对了所有危险操作表单，现状如下——

| 操作 | 二次确认 |
| --- | --- |
| 删除客户/房间/房型/账号/订单 | ✅ 有 |
| 取消订单 | ✅ 有 |
| 退房 | ✅ 有 |
| **办理入住**（3 处入口） | ❌ 无 |
| **房态图改状态** | ❌ 无 |

入住属于超高频操作，不加确认是**合理取舍**（加了反而拖慢前台）。但**房态图上把房间改成"维修中"会直接影响可售性**，建议对这一类变更补确认。

### 3.6 🟡 身份证与手机号未脱敏

客户列表直接明文展示 `idNo`、`phone`（模板中无任何脱敏处理）。客房部账号看不到客户模块（已被权限拦住），但前台同事之间互相可见全部证件号。

**建议**：列表页脱敏显示（`3301**********1234`），详情页按需"点击查看完整"（可记一次操作日志）。

### 3.7 🟡 无打印与导出

酒店实际运营中极高频，当前完全缺失：

- **账单小票 / 结账单打印**（含酒店抬头、消费明细、收退款）—— `bill/detail.html` 已有完整数据，加一个 `@media print` 样式即可
- **订单/账单导出 Excel**（对账、月结）
- **预抵/预离名单打印**（前台早班交接用）

### 3.8 🟡 移动端/平板适配

侧边栏有移动端折叠逻辑（`app.js`），但**表格类页面在窄屏下没有降级方案**（房态图、订单表、账单明细都是宽表格）。酒店前台和客房部实际大量用平板。

**建议**：房态图在窄屏改为单列卡片流；表格用横向滚动 + 关键列固定。

### 3.9 🟡 缺少效率型交互

- 日期输入是原生 `input[type=date]`，没有"今天/明天/后天"快捷按钮（选离店日期时至少要有"次日"）
- 表单无自动聚焦（打开预订页焦点不在第一个字段）
- 全站无快捷键（如 `/` 聚焦搜索框、`Esc` 关闭弹层）
- 长表单无"未保存离开"提醒

### 3.10 🟡 硬删除导致历史断链

房间、房型、客户、账号都是物理删除（`delete`）。虽然 `GlobalExceptionHandler` 会拦住"有外键引用"的删除，但从业务角度：**房型被删后历史订单的房型信息就断了**（当前 `Room.roomType` 是 `EAGER` 关联，房型删不掉，实际操作是加删除限制——但提示不清晰）。

**建议**：改用软删除（`enabled` / `deleted` 标记），列表默认过滤，历史订单仍可追溯。
